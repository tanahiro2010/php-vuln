## 第3章 SQLインジェクションとは（約 3 分）

### S22. 章扉「SQLインジェクションとは」
- 「ではここから、SQLi そのものを説明します」
- 目安: 10 秒

### S23. 一言でいうと
- 「一言で言うと、**ユーザーが入力した文字が、値ではなく SQL の構文として解釈される脆弱性** です」
- 「値と構文の境目が曖昧になる、と言い換えても良いです」
- 「本来、入力された文字はデータベースの中で検索される『値』として扱われるはずです。それが、SQL 文を書き換える『命令の一部』として動いてしまう、というのが核心です」
- 「たとえば `admin` という名前を検索したいだけなのに、そこに紛れ込んだ特殊な記号が SQL の構文として実行されてしまう。この『紛れ込む』という感覚を、次のスライドの図で確認します」
- 目安: 45 秒

### S24. 図解：値と構文の境目
- スライドの図解を指しながら
- 「本来、`WHERE username = '[値]'` の [値] の部分に入るはずのものが、`admin' #` を入れると `#` から後ろがコメントになってしまう」
- 「シングルクォート `'` で値が閉じ、そこから先が構文として動き始める、これが SQLi の本質です」
- 「図の矢印のところを見てください。`admin` のあとの `'` で本来の値の枠が閉じてしまい、その先の `#` はもう『値』ではなく『SQL の一部』として実行されています」
- 「補足：MySQL のコメント記号は `#` か `-- `（スペース付き）。SQLite なら `--` 単独でしたが、MySQL ではダメです。本講義では `#` に統一します」
- 目安: 60 秒

### S25. 起こる被害の4類型
- 「起こる被害は大きく 4 つ」
- 「認証回避、情報漏洩、データ改ざん、データ削除」
- 「今日は 1 と 2 を中心に見ていきます。実際にこの後の事件も、この 2 つのどちらかに当たります」
- 「データ改ざんやデータ削除まで進むと、証拠を消される、記録を書き換えられるところまで行きますが、それは今日は扱いません」
- 目安: 30 秒

## 第4章 なぜ起きるのか（約 4 分）

### S26. 章扉「なぜ起きるのか 文字列結合の危険」
- 「原因を、脆弱なコードを見ながら分解します」
- 目安: 10 秒

### S27. 脆弱なコードを見る（`app_vulnerable.php`）
- 「PHP 側でこう書いています」
- コードを指しながら
- 「これが `app_vulnerable.php` の `/login` 処理、ログインの SQL を組み立てているところです」
- 「`"...{$username}..."` という PHP の文字列補間で `$username` と `$password` を **クエリに直接埋め込んで** います」
- 「見ての通り、入力値のチェックや加工は何もありません。ユーザーが送った文字列がそのまま SQL 文の一部になっています」
- 「これが今日の悪の根源です。この 2 行があるだけで、この後の事件が全部起こります」
- 目安: 60 秒

### S28. 通常入力時の SQL
- 「まず、普通に `username = admin`、`password = admin-secret` と入れた場合」
- 「SQL はこうなります。普通の SELECT 文で、admin のパスワードを照合します。何の問題もありません」
- 「ここまでは想定通りの動きです。問題は、入力に想定外の文字が入ったときに起こります」
- 目安: 30 秒

### S29. `admin' #` を入れると
- 「では `admin' #` を入れると、どうなるか」
- 「クォートで `admin` が閉じて、その後ろの `#` から後は **MySQL にとってコメント**」
- 「つまり、**パスワード条件がまるごと消える**」
- 「スライドの SQL を見てください。`AND password = 'xxxxx'` の部分が全部コメントアウトされて、実行されるのは `WHERE username = 'admin'` だけです」
- 「たった 1 文字、シングルクォートを送っただけで、SQL の意味そのものが変わってしまう。これが SQLi が怖い理由です」
- 目安: 60 秒

### S30. 今のトリックのまとめ
- 「トリックをまとめると、シングルクォートで値を閉じ、`#` で後ろを消す。それだけです」
- 「残ったのは `WHERE username = 'admin'` の 1 行。パスワードを知らなくてもヒットする」
- 「これが認証回避の正体です。特別な知識やツールは不要で、シングルクォートと `#` の意味を知っているだけで成立してしまいます」
- 「次の章では、このトリックを実際の攻撃者の手順に沿って、もう少し丁寧に追っていきます」
- 目安: 45 秒

## 第7章 シナリオC UNION と情報漏洩（約 4 分）

### S50. 章扉「シナリオC UNION と情報漏洩」
- 「認証を突破した次に狙われるのは **情報漏洩**」
- 「入り口の見た目とアクセスできる範囲が違うことを見せます」
- 目安: 15 秒

### S51. この章のゴール
- 「商品検索という **一見無害な入り口** から別テーブルの情報が抜けること」
- 「詳しい実演は後半で。前半では **仕組み** だけ紹介します」
- 「認証を突破するトリックとは別の、もう 1 つの武器を覚えてもらうイメージです」
- 目安: 20 秒

### S52. UNION の考え方
- 「UNION は 2 つの SELECT 結果を **縦に結合** する SQL 構文です」
- 「同じ列数の別テーブルなら、まとめて 1 つの結果として返せる」
- 「本来商品を返すクエリに、顧客テーブルを合流させることができる」
- 「スライドの例を見てください。`products` から `id, name, price` を取る SELECT と、`customers` から `id, email, last_order_total` を取る SELECT を UNION でつなぐと、列数が同じなので 1 つの表としてまとめて返ってきます」
- 「商品一覧のつもりで表示された行に、実は別テーブルの行が混ざっている、これが UNION を使った漏洩の基本形です」
- 目安: 60 秒

### S53. 脆弱版のクエリ（`app_vulnerable.php`）
- コードを指しながら
- 「`app_vulnerable.php` の `/catalog`、商品検索のクエリはこう」
- 「`q` に何を入れても、そのまま `%{q}%` に埋め込まれる」
- 「攻撃者は q に UNION を含む文字列を入れられる」
- 「ここもログイン処理とまったく同じパターンです。ユーザーの入力をそのまま文字列結合しているだけ、というのが共通の原因になっています」
- 「つまり画面も機能も別物ですが、コードの書き方の不備は `/login` とまったく同一です。1 つの書き方の悪習が、サイト中の複数の画面に同じ穴を空けます」
- 目安: 45 秒

### S54. 何が起きる？（後半で実演）
- 「q に `%' UNION SELECT id, email, last_order_total FROM customers #` を入れると、LIKE の文字列を閉じてから UNION で顧客テーブルを合流させられる」
- 「結果、商品一覧の画面に顧客メールが並ぶ」
- 「これが本来のスコープを越えた漏洩の代表例です」
- 「第1章の事件2で見せたあの画面が、まさにこの仕組みで起きていた、ということがここでつながります」
- 「認証回避は『入る』ための攻撃、UNION は『中の情報を持ち出す』ための攻撃です。役割が違う 2 つの武器がそれぞれ揃うと、被害はさらに大きくなります」
- 目安: 45 秒

### S55. 後半で見せる結末（予告）
- 「後半でやる実演はこんな結末です」
- スライドの画像を指して「Name 列に顧客メール、Price 列に注文金額」
- 「後半で 1 個ずつ組み立てて実演します。今日はまず、この結末に至る仕組みだけ持って帰ってください」
- 「第1章で見せた事件2の画面と同じものが、後半ではもう一度、今度は種明かし付きで登場します」
- 目安: 30 秒
